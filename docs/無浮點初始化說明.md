# 整個程式不使用浮點：離線參數表

## 問題

RV64IMC 沒有浮點硬體。推論（Invoke）本來就是純整數，但 LiteRT Micro 在**初始化**（`AllocateTensors()` → 每個運算的 `Prepare`）時，會用 float/double 把模型裡的 scale 換算成整數參數。編譯到 RV64IMC 後，這些計算全部變成軟體浮點函式呼叫，原本共 **409,074 次**（計入 `frexp`、`floor` 等數學函式；只算四則運算與轉換時是 386,606 次）。依呼叫來源（以四則運算與轉換計）：

| 來源 | 計算內容 | 軟體浮點呼叫 |
|---|---|---:|
| GELU（自己寫的 kernel） | 256 格查表：`0.5·x·erfc(−x/√2)` | 約 228,000 |
| FULLY_CONNECTED、CONV_2D | per-channel requant 的 multiplier/shift | 約 154,000 |
| ADD、SUB、MUL、MEAN、BATCH_MATMUL、RSQRT、QUANTIZE | requant 的 multiplier/shift | 約 4,500 |
| SOFTMAX | input multiplier、diff_min | 約 190 |
| CONCATENATION、STRIDED_SLICE | scale 相等檢查、`ceil(float)` | 10 |

## 做法

這些參數只取決於模型（scale、zero-point），與輸入圖片無關，所以可以**離線算好**，就像量化模型本身是在電腦上用 Python 產生的一樣（規格書允許把模型參數離線轉成靜態資料）。

```
電腦（x86）                                          RISC-V（Spike）
同一份 LiteRT Micro 原始碼                            同一份 LiteRT Micro 原始碼
TFLM_OFFLINE_PARAMS=1（記錄）                         TFLM_OFFLINE_PARAMS=2（重播，預設）
  AllocateTensors()                                     AllocateTensors()
  Prepare 照原本方式用浮點計算 ──► offline_params.bin ──► Prepare 直接讀表，不做浮點
                                   （.incbin 嵌入執行檔）
```

- 電腦端程式：`runtime/tools/gen_offline_params.cc`，`make` 時自動編譯並產生 `runtime/build/offline_params.bin`（464 筆，186,780 bytes）。
- 每筆參數以「運算編號 + 欄位編號」為鍵：`runtime/tflm/tensorflow/lite/micro/offline_params.{h,cc}`。
- 用**同一份 C++ 程式碼**記錄，而不是用 Python 重寫一次公式，避免兩邊公式不一致。
- 兩個只是「檢查」的浮點比較（CONCATENATION、SOFTMAX 的 scale 相等檢查）改成位元比較；STRIDED_SLICE 的 `ceil(float)` 改成等價的整數除法。

修改過的 LiteRT Micro 檔案都標有 `[期中project 修改]`：
`micro_interpreter_graph.cc`、`kernels/fully_connected_common.cc`、`kernel_util.cc`、`batch_matmul.cc`、`softmax_common.cc`、`reduce_common.cc`、`mul_common.cc`、`add_common.cc`、`sub_common.cc`、`elementwise.cc`、`quantize_common.cc`、`concatenation.cc`、`strided_slice_common.cc`，以及 `runtime/kernels/gelu_int8.cc`。

## 驗證（三種互相獨立的證明）

| 檢查 | 指令 | 結果 |
|---|---|---|
| 1. 參數正確：目標端照原本方式（軟體浮點）算一次，逐筆與離線表比對 | `make audit` | 464 筆，**不一致 0 筆** |
| 2. 執行期計數：所有軟體浮點函式用 `--wrap` 攔截計數，從開機到結束 | `make run` | `fp_calls_total=0` |
| 3. 執行期追蹤：Spike PC 直方圖中，60 個軟體浮點/數學函式被執行的指令數；F/D 浮點指令數 | `make analysis`（`scripts/check_nofp.py`） | **0**、**0** |

第 3 項也拿舊做法驗證過工具本身：舊做法的初始化有 24,593,609 條指令落在浮點函式裡（`__mulsf3`、`__muldf3`、`erfcf`…），工具會判定 FAIL。

推論結果仍與 Python LiteRT 參考答案**逐位元相同**（1000 個輸出 0 個不一致）。

## 效果

| | 原本（Prepare 用浮點） | 離線參數表 |
|---|---:|---:|
| 整個程式的浮點呼叫 | 409,074 | **0** |
| 初始化指令數 | 38,557,552 | 13,378,206 |
| 推論指令數 | 12,617,761,177 | 12,617,761,175 |
| 執行檔 .rodata | 6,621,088 | 6,807,456（多了 186,780 bytes 的參數表） |

推論指令數只差 2 條，是 `main.cc` 改動造成的程式碼位置差異；每個運算的指令數完全不變。

## 使用

```bash
cd runtime
make            # 第一次會先編譯電腦端工具、產生 build/offline_params.bin，再編譯 RISC-V 程式
make run        # RESULT ... fp_calls_total=0 ... status=PASS
make audit      # 測試：離線表 vs 目標端浮點計算
make OFFLINE=0  # 對照：原本做法（build/deit_float.elf）
```

換模型（重新量化）後，`build/offline_params.bin` 會因為依賴模型檔而自動重新產生。
